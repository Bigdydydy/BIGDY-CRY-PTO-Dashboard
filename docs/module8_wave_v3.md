# Module 8 波浪引擎 v3：对比 LuxAlgo、柳玉冬语料串联与优化记录

## 1. LuxAlgo Elliott Wave 与本引擎的差异

LuxAlgo 的公开说明只涉及以下几点：单一长度的 pivot（左右各 N 根）拐点、仅 1-5 与 A-C 两种形态、两条规则（浪2不破浪1起点、浪4不与浪1重叠）、在推动浪上绘制斐波那契回撤框、规则被破坏后把形态画成虚线，以及几种提醒（发现新形态 / 形态失效 / 可能开始新推动浪）。

| 维度 | LuxAlgo | 本引擎 | 结论 |
|---|---|---|---|
| 拐点 | 固定 N 根 pivot，单一级别，有确认滞后 | ATR 自适应多级 Zigzag，尾部未确认拐点单独标记 | **保留**本引擎 |
| 形态库 | 推动浪 + ABC | 推动、楔形、单/双/三锯齿、平台、三角形、双/三重联合形 | **保留** |
| 规则 | 2 条硬规则 | 手稿 P1-378，按价格/时间/浪型分类，区分软硬规则并标注页码 | **保留** |
| 子浪 | 不检验 | 用低周期 K 线检验出身（五浪/三浪） | **保留** |
| 失效展示 | 形态失效后改为虚线/点线，并保留历史形态 | 只给出失效位，不保留形态历史 | 可借鉴：形态生命周期（后续工作） |
| 提醒 | 新形态 / 失效 / 可能开始新推动浪 | 无 | 可借鉴：`events` 提醒（后续工作） |
| 价格源 | 可选 high/low 或 close | 仅用 high/low | 低优先级 |
| 级别嵌套 | 无 | v2 只有一个级别 | **v3 已补**：级别阶梯 |

结论：本引擎在规则深度上远超 LuxAlgo，值得借鉴的是它的**形态生命周期与提醒**这套交互，而不是它的识别逻辑。

## 3. 特殊浪型与交替原则

**已覆盖（手稿规则库，硬规则 + 指引）**
- 收缩三角形：规则收缩与顺势收缩（b>a）两种子类；a-c 与 b-d 边界必须收敛，交点须在 e 浪之后；c、d、e 子浪越线不超过 10%。
- 平台形：规则平台形、扩散平台形（穿头破脚：b 越过 a 起点，c 跌破 a 终点）、顺势平台形（b 越过 a 起点，c 未到 a 终点）。
- 联合调整：双锯齿、三锯齿、双重横向整理（w-x-y）、三重横向整理（w-x-y-xx-z），均带手稿中的 x 浪、时间、总量限制。

**v3 新增**
- 子形态识别：在一段腿内部的低级别拐点上（多个阈值），用同一套规则库匹配 7 种调整浪型，全部硬规则通过才算成立。
- 交替原则 I2：原先只是占位，不做判定（「人工指引项，自动判定从略」）；现在真实计算。「陡」= 锯齿族，「横」= 平台 / 三角 / 联合；「简单」= 单一形态，「复杂」= 双重 / 三重。浪2与浪4一陡一横或一简一繁即为交替。交替是指引，只影响评分，不否决计数。
  - 浪3运行中：由浪2形态预判浪4（浪2陡 → 浪4预期平台形 / 三角形 / 联合形，回撤偏浅、用时偏长）。
  - 浪4运行中：列出仍然成立的形态，逐日排除，对应柳玉冬「它或者是平台形、联合形、三角形…平台形可以否定」。
  - 子浪数据不足时，退回以回撤深度和用时作代理判断，并在界面上注明「代理」。
- 组成部分：联合形和双 / 三锯齿会识别 w、y、z 各自是什么形态。CG5 检查三角形只能作最后一个组成部分，WG5 检查双锯齿的组成部分应为锯齿形。

**楔形与失败第五浪（手稿第 10-11 章缺失，补主流 EWI 条则并标「通用」）**
- 楔形只出现在四个位置：引导楔形在浪1 / a浪，终结楔形在浪5 / c浪。浪3、b浪不会是楔形。
- 结构：引导楔形为 5-3-5-3-5 或 3-3-3-3-3；终结楔形为 3-3-3-3-3。所以 5-3-5-3-5 一定是引导楔形，3-3-3-3-3 要看位置：起点是之前 1.5 倍楔形长度窗口内的反向极值，算新趋势起点（引导）；同向趋势已运行一段，算趋势末端（终结）。
- 出身检验按位置区分：推动浪浪1（M9）与锯齿 a浪（Z0）可以是推动浪或引导楔形；浪3（M10）只能是推动浪；浪5（M11）、锯齿 c浪（Z7）、平台 c浪（F8）可以是推动浪或终结楔形。小级别能数成五浪时，先按推动浪找，找不到再按楔形（浪4切入浪1）找，并在名称上标注「浪5为终结楔形」等。
- 楔形规则：D1 浪4必须切入浪1；D3 / D5（硬规则）规定收缩楔形 4<2、5<3，扩散楔形反之；D4 检查浪1/3/5 结构一致且与位置相符。
- 楔形完成后的目标：终结楔形结束后通常急速回到楔形起点（推动浪浪5为终结楔形时即浪4终点）；引导楔形之后的浪2回撤偏深（0.618 / 0.786）。
- 失败第五浪：M6（P204）要求浪5未越过浪3终点时长度不小于浪4的 0.7 倍；M12 要求内部仍须走满五浪，否则更可能是浪4未完；G9 为指引——失败第五浪通常出现在特别强劲的浪3（≥1.618×浪1）之后。只有在浪5完成后才标注「失败第五浪」。

**扩张三角形（手稿第 6 章只讲收缩三角形，补主流 EWI 条则并标「通用」）**
- 各段为三浪，边界线 a-c 与 b-d 发散。硬规则：E1 c>b（c 终点越过 a 终点）、E2 d>c（d 终点越过 b 终点）、E3 e≥0.5×d。指引：EG1 b>a、EG2 e 常越过 a-c 线、EG3 相邻放大倍数不宜远超 1.618（否则更像推动浪）。
- 位置与收缩三角形相同；交替原则的浪4预期、联合形「三角形只能作最后一个组成部分」（CG5）同样适用；画浪工具 abcde 同时按收缩 / 扩张两种三角形解读。

**局限**
- 楔形的浪5越过 1-3 线（throw-over）目前未单独识别。
- 当浪4是扩散平台形时，其 b 浪会越过浪3的顶点，主级别会把浪3的终点记在 b 浪处（即「正统顶点」问题）。在形态层面，扩散平台形可以识别；但作为浪4的子形态，目前识别不到。

语料依据：在含图解的 496 帖中，联合形出现 97 次、平台形 54 次、三角形 22 次、双锯齿 24 次、单锯齿 21 次。浪4被描述为平台形 / 联合形 / 三角形，浪2多为单锯齿。

## 3.5 时间规则

**作为判定条件（一直都在）**：手稿的时间硬规则共 20 余条，都在假设搜索阶段剪枝，违反即不产生计数，并在阻碍诊断中写明。例如 M7「浪2时间不超过浪1的9倍」（P34）、M8「浪4时间超过浪3的2倍即否决」（P43）、Z5/Z6、F6/F7、T13/T14、W6/W7、C3/C4、X5–X9，以及同级别比例 L2/L4（反向浪用时不少于前一段的 8%）。时间用分析周期的 K 线根数度量。

**前瞻截止日期（v3 新增）**：柳玉冬把时间规则当截止日期用，例如「b浪应该在4月7日之前结束」「三角形交叉点在8月26日，必须在此之前突破」「根据时间规则，蓝点到红点必须结束」。原引擎只做事后过滤，现在对运行中的那一浪给出三类信息，都附在候选的 `timeWindows` 里：
- `deadline`：由硬时间规则反推的最晚结束日，逾期则该计数作废。
- `typical`：由时间指引给出的常见结束窗口；已经超出时会提示该浪偏长。
- `apex`：收缩三角形 a-c 与 b-d 边界的交点日期。

## 3.6 LuxAlgo 源码（Pine v5，522 行）

已阅读源码。它的实际算法如下：
- 同时运行 3 组 pivot（长度 4 / 8 / 16，对应三个级别、三种颜色）。
- 每出现一个新拐点，只检查最近 6 个点：浪3非最短、浪5终点越过浪3终点、浪2不破浪1起点、浪4不入浪1。
- 推动浪之后紧接的 a-b-c 必须在 0→5 的 0.854 回撤之内，且 b 不越过浪5；从 c 向右画一个「时间 = 浪2到c」的价格框，价格跌破框底时打红叉。
- 形态延伸后若失效，改为虚线显示；最多保留最近 15 个形态；提供 5 种提醒。
- 画 0.5 / 0.618 / 0.764 / 0.854 四条斐波那契线，0.854 被跌破时改为红色虚线。

它没有任何时间规则、比率指引、子浪检验或平台 / 三角 / 联合形。**不建议融合它的识别逻辑。** 可以借鉴的是三项交互机制，需由我们自行实现，不能复制代码（许可为 CC BY-NC-SA 4.0：署名、非商业、相同方式共享）：
1. 多级别同屏：在图上同时画出高一级别与本级别的计数，类似柳玉冬的多色嵌套画法。
2. 形态生命周期：在历史 K 线上保留已完成的计数，失效后改为虚线，并提供「新形态 / 失效 / 可能新起点」提醒。
3. 推动浪后的调整区与时间框：回撤区配合时间宽度，被击穿即标记。

## 3.7 多级别画浪（界面只保留画浪）

Module 8 的界面只保留画浪：框选分析、智能扫描、并列候选、出身校验、承前启后、级别阶梯等由自动数浪驱动的面板已移除（服务端 `/api/wave/analysis` 接口保留）。

**操作**：选画浪工具，在图上依次点击各浪端点；画满或「结束本浪」后加入画板，**不自动评估**。可以继续画子浪，也可以切换到 1H / 15m 画更细的子浪，已画的浪在各周期都会显示。画完点「评估全部」（Enter）。Esc / 右键取消正在画的浪，Backspace 撤销点或删除最后一个浪，列表里的 × 删除单个浪。

**母子关系**（`buildSketchTree`）：一个浪的时间跨度落在另一个浪的某一段之内（容差为母浪周期的一根 K 线），它就是那一段的子浪；有多个可选母浪时取跨度最小者，所以可以嵌套多层。跨越了另一个浪拐点的浪、同一段里画了两个子浪，都会标出来。

**整体评估**（`evaluateUserSketch`）由内向外进行：
1. 每个浪按自己的周期评估（手稿铁律、低周期子浪证伪、画完后的走势检验），子浪判定用更低周期：4H 用 15m / 1H，1H 用 15m / 5m，15m 用 5m。
2. 子浪的结论成为母浪该段的结构判定（取代引擎自动探测），并且子浪的端点固定母浪的拐点。三角形的 e 浪终点、扩散平台的 c 浪终点都不是该段的极值，不能吸附。
3. 子浪与母浪该段的一致性：方向相同；类别相符（驱动段要五浪，调整段要三浪）；楔形只能在浪1 / a浪（引导）或浪5 / c浪（终结）；三角形只在浪4、b浪、x浪或联合形最后一段，画在浪2 判为存疑并说明；双 / 三锯齿的组成部分应为锯齿形。
4. 浪2 与浪4 都画了子浪时，按交替原则给出提示（指引，不影响判决）。
5. 整体结论取所有浪中最差的判决。

## 4. 修正的缺陷

1. 浪5上限原为 `浪4 + 0.382×浪3`，缺乏依据。当浪3短于浪1时，正确上限应为 `浪4 + 浪3长度`（否则浪3成为最短浪）。
2. 五浪完成后的回撤原以 `浪1+浪3+浪5` 之和为基准，现改为 `|浪5 − 浪0|`，并补上 0.2 起点和 0.8 极限两档。
3. 前端调用 `analyzeOrigin(cand, {bars})` 时缺少 `structCache`，导致每次研判都抛出 `reading 'has'` 异常。另外，腿段原按切片相对 idx 去截取全量 K 线，框选后截到的窗口是错的；现已改为按时间截取。
4. 计算段内最大回撤时，原先把起点那根 K 线的另一端影线（发生在拐点之前）也算了进去，已修正。
5. 子浪计数的驱动浪快检跳过了标为「慢速」的规则，I1（浪4不入浪1）因此从未参与，小级别上推动浪和楔形无法区分。现在 I1 无 K 线时退化为端点检验，照常参与。
6. 末浪未确认时，原先所有「最低要求类」规则一律暂缓，连只涉及早已确认拐点的规则也暂缓（例如楔形「浪4须切入浪1」在浪5运行中失效）。现在只有规则涉及的最后一个点就是未确认末点时才暂缓。
7. 自动计数判断引导 / 终结楔形时，原先看的是楔形之前隔一段的那段走势；拐点高低交替，那一段必然与楔形同向，结果永远判为「终结楔形倾向」。现在改按位置判断（见第 3 节）。
8. 三角形越线检验（T11 / T12）原先把端点那根 K 线的另一端也算作越线，但那一端属于相邻的浪。现在奔向的边界不计起点 K 线，离开的边界不计终点 K 线。

「引擎方向」是一个朴素规则：监测点守住就延续当前段方向，被破就反向。它只作为基线，不是交易信号。SNDK 和 MU 的样本太少，不足以下结论。

发现：

- 柳玉冬的监测点通常在现价 1~3% 之外，并且低于最近 72 小时的最低点，说明它们来自他的日线子浪计数。任何单一的 1h 摆动点规则与他的监测点中位距离都在 2~3.5%。
- 斐波那契比例看似能对上（最佳匹配中位距离 0.12%），但把监测点价格随机扰动 ±2% 后匹配度几乎不变，说明这只是候选价位太密造成的伪相关。**因此没有把任何比例硬编码成「柳氏监测点」**。
- 引擎的监测点被明确定义为「主级别当前段内的小级别拐点」，比柳玉冬的逐日监测点高一个级别，界面上如实这样说明。

## 5.1 监测点级别的回测调参（`scripts/liu_threads/tune_monitor.js`、`monitor_roles.js`）

**做法**：语料中有币安 TradFi 合约映射、且带监测点的帖子，按日期前 60% 训练、后 40% 检验；另加人工标注案例 `data/liu_manual_cases.json`（用户转述的柳玉冬判断，目前只有 2026-10-02 的 BTC 一例）。每例只用发帖前的 1h K 线。

**指标一：与柳玉冬监测点的距离——不能当训练目标。**「固定放在现价下方 4.2% / 上方 4.7%」的零模型，在检验段的中位距离为 2.07%，反而优于任何结构规则（最好的 3.03%）。说明柳玉冬的监测点虽然多半就是某一级的真实拐点（46% 与某个拐点相差不到 0.5%），但看不出他取的是哪一级、第几个，靠「级别 × 名次」这类简单规则学不出来。这与第 5 节的结论一致：候选价位太密，容易造成伪相关。

**指标二：结局——监测点事后有没有用。**在 5 日内被破，且之后 3 日继续向破位方向走，算「真破位」；没被破，且 5 日后沿原方向走，算「守住」。两者都算有用。检验段 51 个监测点的结果：

| | 有用率 | 破位准确率 |
|---|---|---|
| 柳玉冬 | 60.8% | 33.3% |
| 引擎·旧规则（本段幅度 6%） | 47.1% | 40.9% |
| 引擎·自然子级别（现行） | 54.9% | 47.2% |
| 零模型（固定 4%） | 56.9% | 23.8% |

零模型的有用率主要来自「守住」：监测点放得远，自然很少被破；但一旦被破，多半是假破位。

**结论与改动**：引擎的监测点改为在「自然子级别」上选——由粗到细，取第一个能把本段分出 ≥3 段的阈值（`MONITOR_DEGREE_MULTS`），取代固定的 6%。这是唯一在训练段和检验段上都优于旧规则的改动（训练段有用率 56.6% → 59.2%）。样本不大，提升幅度也有限。

**BTC 人工案例暴露的缺口（尚未实现）**：柳玉冬用 80026 判断「74887→87397 是整个浪 5 走完，还是只是浪 5 的第 (i) 子浪」。引擎的「当前段」取的是 82500 以来的小反弹，监测点约 85419，与 80026 相差约 6.7%。引擎也不会主动提出「刚完成的五浪只是上一级某一浪的第 (i) 子浪」这一情景。下一步要补上「重新定级」的情景，并按情景给出各自的监测点。

## 1. 后端问题

### 1.1 `/api/market-data` 过重（高）
- 证据：本地实测 raw 2,266,619 B / gzip 349,724 B，首次 4.75 s，第二次 1.54 s。其中 `blockTrades` 1.19MB（`whaleBlocks` 675KB + `icebergClusters` 515KB），`termPremium` 670KB。
- 原因：每个请求都重新跑全部分析器（ATM、Smile、Skew、60 天大宗聚合、做市商全链 ±20% 滑动重估 + 5 档折扣敏感性），算完才算 ETag，所以 304 也省不了 CPU；`termPremium.series` 与 `/api/term-premium` 完全重复。前端 `public/app.js:2909` 不分视图每 30 s 轮询一次。
- 建议：
  1. 按 `dataVersion` 缓存整份分析结果，输入没变就直接复用序列化后的字节和 gzip 结果。
  2. `market-data` 去掉 `termPremium.series`、大宗明细分页（默认 Top N，展开再取）。
  3. 前端只在期权/大宗视图可见时轮询 market-data。

### 1.2 构建失败没有冷却，持续打上游（高）
- 证据：`server/etf_linkage_engine.js:770-779`，构建失败后返回旧缓存，但不记录失败时间；下一次请求再完整重跑一遍。本地连续请求每次 3.9–6.2 s，全部失败。
- 影响：CoinGlass/CFTC 被反复请求，容易被限流，反过来拖累同样走 CoinGlass 的 CDRI、杠杆归一化、基差资金费。
- 建议：失败后至少冷却 10–30 分钟（`upstream_mirror.js` 已有 `FAILURE_COOLDOWN_MS` 的写法，可以抽成通用工具）。其他「失败即回退旧缓存」的模块也按同一模式排查。

### 1.3 每 30 秒的行情刷新里带着按天变化的大请求（中）
- 证据：`server/data_fetcher.js:321` `fetchDvolHistoricalStats` 无 TTL，每轮都拉 2 年 DVOL 日线 + 120 天永续小时线 + 30 小时 DVOL；`iv_history`、`skew_chart` 也是日频（`gap: '1d'`）却每 30 s 拉。
- 建议：日频源加 10–30 分钟 TTL，30 s 轮询只拉真正的实时源（atm/gex/smile/trades）。

### 1.4 运行时写入受 git 跟踪的文件（高，工程）
- 证据：本次本地运行后 `data/macro_chart.json`、`cdri_data.json`、`ssro_chart.json`、`gold_correlation.json`、`coinbase_liquidity.json`、`term_premium_history.json`、`mstr_disclosures.json`、`block_trades_BTC.json` 都被服务器改写；这些文件同时由 Actions 提交。本地 `main...origin/main [behind 168]`。
- 仓库其实已有正确模式：`coinbase_liquidity_history.local.json`、`option_oi_history_BTC.local.json`、`smart_money_BTC.local.json` 等「本地补采写 .local、权威序列由 CI 提交」。
- 建议：把上面这批文件也统一成「运行时写 `*.local.json`（gitignore），启动时读 `max(本地, 仓库归档, GitHub raw)`」。
- 附带：`server/trade_store.js` 本地改动后每次轮询都整文件重写（60 天约 3–4MB，每 30 s 一次）。建议只在新增或剪枝时写盘。

### 1.5 限流可被伪造绕过（中，安全）
- 证据：`server/index.js:1259/1393/1451/1561` 取 `X-Forwarded-For` 的**第一个**值当客户端 IP，这个值由客户端自己填。`/api/refresh` 一次会触发 8 组上游请求。另外所有 API 都返回 `Access-Control-Allow-Origin: *`，包括 POST `/api/refresh`。
- 建议：Render 场景取 XFF 的最后一跳（代理追加的真实 IP）；`/api/refresh` 再加一个全局冷却（例如全站 30 s 一次）；POST 接口去掉通配 CORS。

### 1.6 进程级兜底缺失（低）
- 证据：没有 `process.on('unhandledRejection')`；`http.createServer(async ...)` 里 `await handleApiRequest` 没有外层 catch。各路由目前都有 try/catch，所以暂时没出事，但新加路由一漏就会让整个进程退出（Node ≥15 默认行为）。
- 建议：外层 `.catch` 统一返回 500，并加 `unhandledRejection` 日志。`url.parse` 已弃用，可换 `new URL()`。

### 1.7 宏观图的实时现货注入没有校验（低）
- 证据：`server/index.js:1066-1100` 用 `cache.gex.index_price` 覆盖 `points` 最后一点的 `btcPrice`，注释写「if today」但代码没判断日期，也没看该价格的健康状态。
- 建议：只在最后一点日期 = 今天（UTC）且 `greeks_gex` 可用时注入。

### 1.8 Render 上的 McClellan 来源（中，需确认）
- `server/crypto_mcclellan_fetcher.js:303-330` 在服务器上 `exec` Python 管线（240 s 超时）。`render.yaml` 只 `npm install`，Python 依赖大概率不在，所以线上实际只能读部署时带上的 `data/crypto_mcclellan.json`。
- 需要确认的一点：`mcclellan_daily` 的提交信息只有 `[skip ci]`、没有 `[skip render]`。如果 Render 因此每天重新部署 4 次，所有内存缓存和本地档案会被清空（见 4.3）；如果不重新部署，线上 McClellan 就停在上次部署那天。两种都不理想。
- 建议：像 `block_flow`/`liquidity_history` 那样直接读 GitHub raw 归档，服务器不再跑 Python。

### 1.9 唯一失败的测试：测试隔离泄漏（低）
- `test/source_payloads.test.js:206` 断言「无配置时 `strcRateConfigured === false`」，但 `server/mstr_preferreds.js:21` 的 `STRC_RATE_HISTORY_FILE` 写死为仓库 `data/strc_rate_history.json`，没被 `installModuleMocks` 重定向。仓库里这个文件已有 16 个月的 SEC 股息率，测试必然失败。
- 建议：把档案路径做成可注入参数，测试指向临时目录。

### 1.10 CI 使用已停止维护的 Node 20（中）
- 5 条数据管线 `node-version: '20'`（Node 20 已于 2026-04-30 EOL），只有 `data_health.yml` 用 24。建议统一升到 22 或 24。

## 2. 金融上不合理或需要改口径的图表/指标

### 2.1 Coinbase 金字塔基准 3.1× 与实际分布不符（高）
- 证据：`server/coinbase_fetcher.js:304/444/474` 写死 `baseline100_10: 3.1`，体制判定阈值 4.5/5.0/5.5/6.0 也是常数。用自家 `/api/coinbase-liquidity-history` 的 523 个小时样本算 100bps/10bps：p5 3.99、p25 6.38、**中位 7.39**、p75 8.54、p95 11.07；>6× 的占 82%，≤3.5× 的只占 3%。当前判定结果是「⚡ 金字塔形变 / 防线下移」（8.3×）。
- 建议：基准和阈值改为档案的滚动分位数（与同页「韧性评分」的做法一致：自身 75%/25% 分位）。

### 2.2 聪明钱信号按命中率加权（高）
- 证据：`server/block_insight.js:416-441`，权重 `p = (胜+1)/(样本+2)`。页面数据：买入波动率命中率 27%、平均结算 **+0.31₿**；卖出波动率命中率 65%、平均 **−0.07₿**；方向看空命中率 61%、平均 −0.19₿。
- 问题：期权买方天然低胜率、高赔率，卖方相反。按命中率加权会把赚钱的买波动率结构降权，把亏钱的卖波动率结构升权。每组已结算样本只有 18–52 个，二项分布标准误约 7–12 个百分点，35% 和 60% 的差别多数不显著。
- 建议：权重改为期望盈亏（按权利金或 Vega 标准化）或盈亏比；每组显示置信区间；样本 <30 时只展示、不参与「胜率加权方向倾向」。

### 2.3 ETF 期现套利用的是 Deribit 基差（中）
- 证据：`server/term_premium_engine.js:27-39`「ETF 期现套利净年化 +0.08%」= Deribit 90D 基差 − 3M 美债 − ETF 成本。
- 问题：买 ETF 的机构用 CME 期货对冲，不用 Deribit。CME 基差通常高于离岸，两者差异恰好是这类分析想看的东西。
- 建议：ETF 套利一栏换 CME 基差（CoinGlass 有 CME 合约价或基差）；拿不到就把标题改为「Deribit 基差近似」。「美债 + 3.5% 机构门槛」也应注明是经验假设。

### 2.4 0D 资金费率与期货基差混在一条期限曲线上（低–中）
- 0D 点是 7 日**已实现**资金费均值，当季/次季是**锁定**的远期基差，一个向后看、一个向前看。「曲线斜率」磁贴在资金费比当季高 3pp 时显示「永续高于交割（短端多头拥挤）」，但旁边的数字是期货之间的斜率（−0.01pp），读起来像斜率本身说明了拥挤（`public/app.js:5782-5791`）。
- 建议：资金费反转单独做一个磁贴，斜率磁贴只描述斜率。

### 2.5 两套 mNAV 同屏（中）
- 宏观卡片「EV / BTC 市值（旧口径参考）1.10× 估」与下方「官方口径 mNAV 1.18×」并列。旧口径在 2026-09-12 之后是股价外推估算，并假设新增 BTC 全部用普通股 ATM 融资（`server/macro_fetcher.js` mnavAnchor 段），而 2025–2026 年大量资金来自优先股，这个假设会让估算逐渐偏离。
- 建议：旧口径序列截止到最后一个真实数据日，之后不再外推；主卡片只显示官方口径。

### 2.6 期限利差口径（低）
- README 写「US10Y/US02Y」，代码与页面实际是 10Y − 1Y（`server/macro_fetcher.js:547`）。10Y−2Y 或 10Y−3M 才是常用的衰退指标，建议改用 `DGS2` 或在 README 更正。另外 DGS1 是 1 年期国债恒定期限收益率，不是 T-Bill，标签「US 1Y T-Bill」不准确。

### 2.7 做市商「过去 24h 已触发对冲流」分解对不上总数（中）
- 页面：总额 +$190.0M，分解 Gamma +46.3 / Vanna +30.7 / Charm −7.2，合计只有 +69.8M。
- 原因：`server/dealer_engine.js:701-721` 用全链把时间倒拨 1 天重估，当天到期的日度合约（剩 1 小时）在倒拨后 Delta 从近似阶跃变平滑，产生很大的 Delta 差，而一阶近似用的是此刻的 Charm。
- 建议：剩余期限 < 回看窗口的合约单独列为「临期项」，或把差额显式标为「高阶 / 临期残差」。

### 2.8 其他小口径问题
- 黄金：页面写「对数收益率」（`public/index.html:2879`），代码是简单收益率（`server/gold_fetcher.js:105`）；README 声称 30D/90D/180D 相关，代码只有 30D；PAXG 周末 24/7 交易而伦敦金休市，周末收益会稀释相关系数，可以考虑只用工作日；BTC 流通量常数 19.8M 用于全部历史（2023 年约 19.3M）。
- ATM IV 卡片「1M-3M Spread: -1.8%」等单位应为「波动率点」；Smile 卡片 `+2.2%` 与正文「+2.2 点」混用。
- 「方差风险溢价 VRP」实际是 IV − HV（波动率点），严格说是波动率风险溢价。
- 期限分档「10–16 周（季度合约）」当前 0 OI，因为季度合约会随时间滚过各档，按期限命名比按合约类型命名更准确。
- STRC「当期收益率 − 1M T-bill 7.98%」用的是月均价 99.31 算出的 12.08%，卡片只显示股息率 12.00% 和 T-bill 4.10%，读者心算得到 7.90%，建议把 12.08% 显示出来。

## 4. 数据调用稳定性与「保险」盘点

### 4.1 现有保险逐项评估

| 保险 | 现状 | 结论 |
|---|---|---|
| 每源健康登记 + `analysisAllowed` 门禁 | 设计扎实、测试覆盖充分 | **有用**，但阈值需按源校准（见下两行） |
| ETF OI 校验「任何 null 即整源失败」 | CME 有休市日，序列出现空值并不反常（具体是哪几天的空值本次未解密核对）；下游 `put()` 和 `lastValueOnOrBefore` 早已能处理空值；10-16 起整模块停更 | **误伤**。`server/etf_linkage_engine.js:274-304` 改为允许 null，只拒绝负数、非数字和最近 N 天全空 |
| `basis_history` 用 ARCHIVE 策略（回执 2h 预警） | 日度归档每天只在 08:00 UTC 产生一行，磁盘回执 2 小时后必然变 STALE | **误伤**。`server/data_health_policy.js:13/32` 回执窗口改为 ≥26h，或按「是否已有今天应有的那行」判断 |
| Data Source Health Monitor 工作流 | 10-19 至今 55/55 失败，原因 `live audit fetch failed`（15 s 超时打 Render 免费实例，冷启动通常 30–60 s）；`webhook not configured` | **失效**。先打 `/healthz` 唤醒并把超时提到 90 s，配置 webhook；否则不如停掉，免得红灯成为常态 |

### 4.2 最大的单点：逆向的私有接口
- Greeks.live DataLab 靠写死在公开仓库里的 RSA 公钥生成 `X-Sign`（`server/crypto_signer.js`）；CoinGlass 靠 AES-128-ECB 解密内部接口（`server/cdri_fetcher.js:93`，`server/macro_fetcher.js:228` 还有一份重复实现）。仓库是 PUBLIC，对方很容易发现并更换密钥。
- 期权板块（ATM IV、Smile、25Δ Skew、GEX、大宗）没有任何备用源；现货价 `spotPrice` 也只取 `gex.index_price`，Greeks GEX 一挂，大宗与 Smile 一起锁死。
- 建议：
  1. 现货价加 Deribit 指数价（`option_marks` 快照里已有 `indexPrice`）作为第二来源。
  2. ATM IV、Smile、25Δ RR/BF 用 Deribit `get_book_summary_by_currency` 的 mark IV 自算（`dealer_engine` 已经在逐合约算 Black-76，插值到固定 Delta 只差一步），作为 Greeks.live 的备用或交叉核对。
  3. 大宗成交备用：Deribit `get_last_trades_by_currency` 带 `block_trade_id` 的成交。
  4. CoinGlass 依赖集中到一个客户端模块，统一限流与冷却。

### 4.3 只存在于服务器本地、重启即丢的数据
- `data/vol_surface_history_BTC.local.json`（本地 9 天，25Δ 偏度贵贱分位要 30 天才启用）、`data/flow_force/`（定稿 K 线）、`*.local.json` 补采。没有任何工作流生产它们。Render 免费实例文件系统不持久，重启/重新部署后清零。

### 4.4 Render 免费实例的现实

## 6. 建议与思考

1. **少一点模块，多一点验证。** 现在有 21 个板块、每张卡都有一段自动生成的研判文字。真正决定这个看板价值的，是这些结论有没有被回测过。仓库里已有 `wave_track_record.js`、聪明钱命中率、`liu_threads/replay` 这类工具，但结果都在 gitignore 里，页面看不到。建议每个给出方向结论的模块，都在卡片上挂一个「这个信号过去 N 次的表现」小表，样本不足就明说「未经验证」。McClellan 自己的元数据里已经写了 `predictive_validation: not_performed`，这个诚实可以推广到所有模块。

2. **阈值都应该来自数据本身。** 金字塔 3.1×、机构门槛 +3.5pp、ETF 流入/成交 ±5%、RR ≤ −3 / ≥ +2、VRP 1/3 点、CDRI 30/60/80……大部分是经验常数。同一页上「韧性评分」已经在用自身历史分位，这是对的方向。建议把常数阈值逐个换成滚动分位，或至少在悬停里标「经验值」。

3. **一个结论只用一个口径出场。** 做市商模块是最典型的例子：口径敏感性分析做得很认真，但主屏上三个翻转位、两套压力数字会让人在关键时刻犹豫。建议主屏只放主口径，敏感性收进「这个结论稳不稳」折叠区，并直接给一句「各口径同号 / 不同号」。

4. **健康系统需要「误报率」这个指标。** 现在的设计只防漏报（不把旧数据当新数据），没有防误报，所以出现了 1.3、4.1 里那种整天黄灯、整源误杀的情况。告警一多就没人看，真出事时也就没人看。可以给 `/api/system/audit` 加一个「过去 7 天每个源处于非 OK 的时长」，超过阈值的源就该回头校准策略。

5. **把对私有接口的依赖当成负债记账。** Greeks.live 与 CoinGlass 是这个项目的两条命脉，而且都不是公开 API。能从 Deribit 公开接口自算的（现货、ATM、Smile、Skew、GEX、大宗）优先自算，私有接口降为交叉核对。这会让项目从「漂亮的镜像」变成「自己的引擎」，和你在 `dealer_engine` 里已经走的方向一致。

6. **线上和本地要有一个统一的数据真相源。** 现在是 CI 写仓库、Render 读部署时的副本或 raw、本地服务器又自己写同一批文件，三方各有一份。建议收敛成：CI 是唯一的归档生产者 → 归档放独立分支或对象存储 → 服务器（本地和线上）只读归档 + 叠加实时点，运行时产物一律 `.local`。

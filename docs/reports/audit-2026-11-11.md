## 1. 严重

### 1.1 畸形请求让进程退出

三个请求各自都能让服务进程以退出码 1 结束：

| 请求 | 抛错位置 | 原因 |
|---|---|---|
| `GET /api/wave/klines?symbol=a&symbol=b` | `server/index.js:1450` | 重复参数被解析成数组，数组没有 `toUpperCase` |
| `POST /api/wave/evaluate`，请求体 `null` | `server/index.js:1626` | `JSON.parse('null')` 得到 `null`，随后读 `payload.symbol` |
| `POST /api/wave/analysis`，请求体 `{"symbol":1}` | `server/index.js:1518` | 数字没有 `toUpperCase` |

三处都在 `try` 之外。外层 `http.createServer(async …)` 里的 `await handleApiRequest(…)` 没有 `catch`（`server/index.js:1876-1902`），全仓库也没有 `unhandledRejection` 处理，Node 15 以后未处理的拒绝会直接终止进程。

复现方式：在测试沙箱副本里加载 `server/index.js`、监听本地随机端口、逐个发送上述请求。对照请求（`symbol=DOGEUSDT`）返回 400 且服务存活；另外三个请求都没有响应，进程打印 `TypeError` 后退出。

影响：Render 会自动重启，但内存缓存、`*.local.json` 补采和 `data/flow_force/` 定稿 K 线全部清零；重复发送即可让服务持续不可用。上次报告 1.6 把它列为「低，暂时没出事」，现在有了具体触发方式。

建议：
1. 外层加 `try/catch`，统一返回 500。
2. 加 `process.on('unhandledRejection')` 记日志。
3. 查询参数统一用 `String(...)` 取值；请求体不是普通对象时返回 400。
4. 补三条回归测试。

## 2. 高

### 2.1 `?force=1` 是不设防的缓存旁路

11 个 GET 接口接受 `force=1`（部分还接受 `refresh=true`），不鉴权、不限流：

`/api/etf-linkage`、`/api/leverage-norm`、`/api/mstr-preferreds`、`/api/mstr-disclosures`、`/api/macro-chart`、`/api/cdri`、`/api/ssro`、`/api/flow-force`、`/api/coinbase-liquidity`、`/api/gold-correlation`、`/api/crypto-mcclellan`（`server/index.js:1061-1261`）。

各模块的 `force` 分支都跳过 TTL 直接重建（例如 `server/macro_fetcher.js:988`、`server/ssro_fetcher.js:492`、`server/gold_fetcher.js:312`）。单飞锁只合并同时到达的请求，前一次完成后下一次立刻又是一轮完整拉取。`etf_linkage_engine.js:827` 的失败冷却也带 `!force` 条件，同样被绕过。

`/api/crypto-mcclellan?force=1` 额外会在请求路径上同步执行 `execSync('python3 --version')`（`server/crypto_mcclellan_fetcher.js:224-230`），本机装有 Python 时还会启动最长 240 秒的采集管线。

影响：一个循环脚本就能让 Render 的出口 IP 被 CoinGlass、FRED、Yahoo 限流；SEC 请求带着 `SEC_USER_AGENT` 里的联系邮箱，被封的是这个身份。`POST /api/refresh` 有限流，这 11 个 GET 没有，限流形同虚设。

这一条是读代码得出的，没有对线上或上游实际发流量验证。

建议：`force` 只在本机回环地址或带密钥头时生效；其余请求一律走 TTL。

### 2.2 限流可伪造，限流表本身可被撑大

- `server/index.js:1310 / 1444 / 1502 / 1612` 取 `X-Forwarded-For` 的第一个值，这个值由客户端填写。上次报告 1.5，未修。
- `refreshRateLimitMap` 只在超过 1000 条时清理，且只删 60 秒前的（`index.js:1327-1331`）；`waveRateLimitMap` 超过 2000 条后**每个请求**都全表扫描（`index.js:227-231`）。伪造不同 XFF 的洪水下，表在一分钟窗口内无上限增长，扫描成本随之线性上升。
- `/api/market-data` 的 `threshold` 接受任意整数（`index.js:729`），每个新值都触发一次完整重算，缓存只留 24 份。该接口没有限流。
- `/api/wave/analysis` 每次请求都同步重算，不缓存。用测试夹具平铺到 10000 根 K 线实测单次约 0.3～0.4 秒，期间事件循环被占用。
- 所有响应带 `Access-Control-Allow-Origin: *`，包括 `POST /api/refresh`（`index.js:648`）。

建议：Render 场景取 XFF 最后一跳；限流表设硬上限；`threshold` 收敛到几个固定档位；POST 接口去掉通配 CORS。

### 2.3 没有测试门禁

6 个 workflow 没有一个运行 `npm test`，也没有 push / PR 触发的 workflow。Render 跟随 `main` 自动部署，669 个用例只在本地手动跑时才起作用。

`mcclellan_daily.yml` 只跑 `test_breadth.py`，同目录的 `test_structure.py` 不在 CI 里。

建议：加一个 push / PR 触发的 workflow 跑 `npm test` 和两个 Python 测试文件。

### 2.4 运行时写入受版本控制的文件

以下文件既被服务进程改写，又被 Actions 提交或随仓库分发：

`block_trades_BTC.json`、`cdri_data.json`、`coinbase_liquidity.json`、`etf_linkage.json`、`gold_correlation.json`、`macro_chart.json`、`mstr_disclosures.json`、`mstr_preferreds_cache.json`、`ssro_chart.json`、`strc_rate_history.json`、`term_premium_history.json`。

证据：当前 `git status` 有 8 个 `data/*.json` 处于修改状态。`server/trade_store.js:144` 在每个进程的第一次合并时无条件写盘，所以本地每启动一次服务，`block_trades_BTC.json` 就会变脏。

仓库里已有正确做法（`*.local.json` 加 `.gitignore`，共 4 处），这 11 个文件没有跟上。上次报告 1.4，未修。

## 3. 中

### 3.1 大宗成交归档损坏时被静默清空

`server/trade_store.js:39-49`：归档 JSON 解析失败时打一条日志并返回空数组。随后 `recordAndMergeTrades` 把「空数组加本轮新成交」当作合并结果写回同一路径（`trade_store.js:144-145`），60 天历史被替换成最近一个窗口。

这个文件同时被本地服务改写、被 Actions 提交、被 `git pull --rebase` 合并，出现冲突标记或截断并非不可能。CI 里 `block_insight_daily` 走的是同一个函数，清空后的文件会被提交。

建议：解析失败时抛错并拒绝写盘，或先把原文件改名留底。

### 3.2 90D 基差缺失被判成「基差断崖压缩」

`server/term_premium_engine.js:116`：`apr90d < 1.0` 在 `apr90d` 为 `null` 时成立（`null` 被当作 0）。

复现：`evaluateCarryRegime({ apr90d: null, cqApr: 6.2, nqApr: 6.8, tbill: 4.1, … })` 返回 `CRISIS_COMPRESSION`，正文写「90D 基差仅 --，交割合约接近平水甚至贴水」，而当季、次季基差分别是 +6.2% 和 +6.8%。

`apr90d` 为 `null` 是代码预期内的状态（`basis_fetcher.js:250-252`、`term_premium_engine.js:40` 都专门处理了）。它出现的条件是资金费率缺失且没有期限点能把 90 天夹住。当前归档 1046 行里没有这样的行，所以目前没有显示错误。

建议：函数开头对 `apr90d == null` 单独返回「数据不足」。

### 3.3 波浪规则里「较短者」按价格长度选，疑似应按时间

规则文字是「c 浪时间不超过 a、b 中较短者的 10 倍」，实现是：

```js
const mt = g.l[0] <= g.l[1] ? g.t[0] : g.t[1];   // g.l 是价格长度，g.t 是用时
```

同一写法出现在 Z6、ZG7、F7、FG4 四条规则和两张时间表里（`server/wave_engine.js:539, 559, 584, 603, 1961-1962, 1972-1973`）。单锯齿里 b 永远比 a 短（规则 Z2），所以 Z6 实际恒等于「c 用时 ≤ 10 × b 用时」，与 a 的用时无关。

**这是疑点而非确认的缺陷**：手稿 P144 / P201 不在仓库里，无法判断原文的「较短」指价格还是时间。测试里没有任何用例引用 Z6、F7、ZG7、FG4，两种读法都没有被钉住。需要你对照手稿确认。

### 3.4 波浪引擎内嵌的命中率表已过期

`server/wave_engine.js:69` 的 `TRACK_RECORD` 标注 `generatedAt: 2026-10-03`。此后有 37 个与 wave 相关的提交，引擎文件最后一次修改在 10-23。`docs/module8_wave_v3.md` 第 5.6 节自己记录了 10-14 重跑后总体命中 / 期望从 1.054 降到 1.015。

界面在差距 ≥ 5 个百分点时显示「历史上同类计数先到目标 X%（随机 Y%）」（`public/wave_ui.js:1489`）。按内嵌表，「推动浪 · 运行中」是 79% 对 72%，会显示；这组数字描述的是 37 次修改之前的引擎。

建议：重跑 `scripts/wave_track_record.js` 更新内嵌表，或在显示时带上生成日期。

### 3.5 做市商交割断崖预警的口径与措辞

`server/dealer_engine.js:823, 997` 的文案是「占全链 Gamma 绝对量 X%」，前缀是主口径标签（全成交校正）。实际的 `gexShare`（`dealer_engine.js:940-943`）是：

- 按**惯例口径**算的，不是主口径；
- 分子分母是各到期日**净** GEX 的绝对值，同一到期日里 Call 与 Put 已经相互抵消，不是 Gamma 总量。

`expiry_cliff` 预警的触发条件用的是主口径残余 GEX，文案里的占比却是另一套数。属于上次报告「一个结论只用一个口径」那类问题的遗留。

### 3.6 整批严格校验的误伤风险

- `validateIvHistory` 要求历史里**每一行**的 `month1 / month3 / month6` 都是正数（`server/data_fetcher.js:89-99`）。上游任何一行历史出现空值，整个 `greeks_iv_history` 判失败，ATM IV 与 25Δ Skew 两个分析被锁。
- `validateBlockTrades` 遇到一条坏成交就拒绝整批（`data_fetcher.js:44-57`）。

这与 10-16 起 ETF 联动停更 13 天是同一种模式（序列里一个空值让整源失败）。目前没有触发，属于风险提示。

建议：历史序列只校验分析窗口内的行；成交逐条丢弃坏行并记入 `issues`。

### 3.7 归档写盘失败会丢掉整轮刷新

`server/data_fetcher.js:578-579`：先 `recordSuccess('greeks_trades')`，再调用 `recordAndMergeTrades`。后者写盘失败会抛错（`trade_store.js:76`），而这里没有 `try`，于是整个 `doRefreshAllMarketData` 被拒绝，本轮已取到的 ATM、GEX、Skew、Smile 都不会写进缓存。健康登记里 `greeks_trades` 却已经记成成功。

`data_health.yml` 的 cron 是每小时一次。`gh run list` 显示 11-08 06:44 到 11-11 08:26 的 74 小时里只有 12 次运行。GitHub 对定时任务的丢弃在其它管线里是用「每小时排 4 个时段」对冲的，巡检只排了 1 个。

好的一面：上次报告的「55 / 55 全部失败」已经修好，最近 12 次里 8 次成功。

### 8.2 本轮新确认并修复的问题

1. **资金费率空值变为零（中）**。`server/leverage_norm.js:209` 原先用 `Number(null)` 解释资金费率，缺测会计作一次零费率结算并推进覆盖计数。现在拒绝 null/空串/布尔，真实零值保留。
2. **ETF 未公布流量变为零（中）**。`buildEtfTurnover` 原先纳入基金成交额，却把该基金 null 流量加为 0，稀释流入/成交额比。现在流量未公布的日期不参与完整日窗口；原测试里 FBTC=null 却断言作 0 的夹具改为真实零。
3. **成交台账磁盘回退刷新成功时钟（中）**。`server/option_flow_ledger.js` 远端失败后原先对本地文件调用 `recordSuccess`。现在只恢复数据时间，保留未知的成功回执并记录真实失败；未来 `syncedThrough` 也会拒绝。
4. **同毫秒分页丢数据却宣称完整（高）**。`syncLedger` 和 `windowVolumesFromTape` 在时间游标停滞时原先前移 1ms，可能跳过同毫秒未返回成交，然后写入完整台账或“精确成交量”。现在明确失败，不推进完整回执/不生成精确窗口。
5. **SEC 缺少美元余额被算作零现金（中）**。`deriveSecCapital` 将 null `cashUsd` 改成 0，导致缺必需输入仍能计算官方 mNAV。现在保留 null，让官方模型的输入校验拒绝。
6. **期权缺少成交量被压为零（中）**。`compactBookSummary` 原先把缺失 OI/volume 编成 0。现在保留 null；`withProvisionalSnapshot` 会拒绝缺量的快照，避免以假零参与开平仓判断。合法的显式 0 不变。

新增行为测试位于 `test/audit_regressions.test.js`；相关已有 OI/台账/杠杆/做市商测试也已更新或补断言。

# Coinbase 现货秒级插针研究

独立目录，仅处理 Coinbase Exchange BTC-USD 现货。Python 3.10+，无第三方依赖。
研究对象：同一根 **1 秒 K 线的长影线与高成交量同时出现**。整秒成交量不是单笔主动订单量。

## 首次复核

在本目录运行（PowerShell）：

```powershell
python -X utf8 research.py backfill --start 2026-11-18T18:18:00 --end 2026-11-18T19:06:00
python -X utf8 research.py analyze --start 2026-11-18T18:28:00 --end 2026-11-18T18:51:00
python -X utf8 report.py output
python -X utf8 -m unittest -v
```

长期历史先回补，再分析；无时区时间均按北京时间：

```powershell
python -X utf8 research.py backfill --start 2026-10-31T08:00:00 --end 2026-11-18T22:22:40 --workers 12
python -X utf8 research.py analyze --start 2026-10-31T08:00:00 --end 2026-11-18T22:22:40
python -X utf8 report.py output
```

若进程中断，使用同一数据库、相同起止时间和相同 `--workers` 重跑 `backfill`，会从每个 ID 段已有的连续后缀继续。

无时区时间按北京时间 UTC+8 解释；内部保存 UTC 微秒，输出显示北京时间。
时间窗口左闭右开。初次采集含截图前 10 分钟背景及后 15 分钟；分析窗口可以扩至采集区间。

## 数据与完整性

- `data/trades.sqlite` 保存 API 成交 ID、时间、精确价格和数量字符串、maker 方向并去重。为控制长期数据库体积，当前版本不再冗余保存逐笔原始 JSON；原始字段仍可凭成交 ID 从 Coinbase 复核。
- REST 历史分页，先按成交 ID 二分定位结束时间，再向前逐页抓取。定位依赖 ID 与时间有序；采集检查时间顺序、ID 连续及两端覆盖。历史服务可用性需要实际验证，不能保证任意月份均可回补。
- 每次抓取的覆盖与错误写入 `runs`；分页预算耗尽、成交 ID 缺口或错误时标记 partial，分析器拒绝使用未完整覆盖的区间。长期回补把 ID 区间分给 8 个并发读取器，全局请求节流不超过 Coinbase 公共接口 10 次/秒限制；每段默认最多 5,000 页。重跑去重但仍重新抓取，不是断点续传。
- 同一时间戳以 trade ID 排序。无成交秒不制造 K 线，汇总单独计数。历史缺页与无成交秒不能混淆。
- Coinbase `side` 是 maker 方向：buy 对应主动卖，sell 对应主动买。REST 不提供订单 ID，不能据相近时间或方向把多笔成交确定为同一个主动订单。

## 筛选口径

下影线 = min(O,C) − L；上影线 = H − max(O,C)。上下方向和阳线、阴线、平线独立标记，因此不会假设事件只出现在截图中的阴线上。

默认条件全部满足才入选：

- 整秒总成交量 ≥10 BTC（`--min-volume`）；
- 影线 ≥20 美元（`--min-wick-usd`）且 ≥3 bps（`--min-wick-bps`，分母为该秒收盘）；
- 影线占整秒振幅的比例默认不设下限，因为用户要求首先观测的是“影线绝对长度 × 成交量”；比例仍写入结果，需要时用 `--min-ratio` 再筛。这个比例描述形态，不等于实际回收路径或回收速度。

这些是待截图校准的初始阈值，10 BTC 来自用户描述；其余没有经过收益优化。
另记过去 600 秒中非零振幅秒的中位数、样本数及影线倍数，基准不包含当前秒；默认不以倍数筛选。可用 `--min-multiple 5` 开启。稀疏时须查看样本数。
影线区间成交量仅累计严格落在实体外的逐笔成交；边界不计入。`max_print_btc` 是最大一笔撮合记录，不能当作最大主动订单量。

## 输出

- `output/bars_1s.csv`：所有有成交秒的 OHLC、量、上下影线、主动方向量、影线区间量。
- `output/volume_candidates.csv`：仅按成交量筛选，方便检查短影线或秒边界造成的漏检。
- `output/events.csv`：两个维度同时满足的事件，含 `candle_color` 以及 5/30/60/300/900 秒事后价格变化。
- `output/summary.json`：覆盖、空秒数量、实际阈值，以及按上下影线和阳/阴/平线拆分的事件数。

事后变化从事件秒收盘到目标秒收盘，以 bps 表示，不按影线方向翻转。目标秒无成交时最多向前取 5 秒并记录报价年龄；超出完整采集覆盖或价格太旧则留空。分析器自动使用该次完整采集里事件窗口前最多 10 分钟、后最多 15 分钟的数据计算背景与结果，输出事件仍限于 analyze 指定窗口。实际背景范围写入 summary；若历史背景不足，基准可能不足 600 秒。

本阶段是事件研究与数据核对，未实现可执行交易回测。收盘价只是研究基准；后续回测须从事件秒结束之后设置可成交的进场规则，加手续费、滑点、持仓与退出规则，不能假设在针尖成交。
第二张图的一连串小插针属于后续独立检测器，当前高量长影线筛选不宣称覆盖它。

## Kraken XBT/USD 参照（`kraken.py`）

只以 CB 事件为主体：逐个 CB 事件检查 Kraken 同一时间是否同向移动；Kraken 独有的插针不处理。

```powershell
python -X utf8 kraken.py backfill --start 2026-11-18T00:00:00 --end 2026-11-19T00:00:00
python -X utf8 kraken.py compare --start 2026-11-18T00:00:00 --end 2026-11-19T00:00:00 `
  --cb-db data/coinbase.sqlite `
  --events output/2026-10-31_to_2026-11-19/events.csv `
  --bars output/2026-10-31_to_2026-11-19/bars_1s.csv.gz --output output/kraken_2026-11-18
```

- 数据：Kraken 公共 `Trades` 接口按 `since` 翻页，校验成交 ID 连续，约 1 次/秒；一天约 170 页、17 万笔。`side` 为主动方（b/s）。
- 口径：两边都以窗口 [s−1, s+2) 之前最后一笔成交为锚，取窗口内向影线方向的极值，单位 bps。幅度比 = Kraken 偏离 / CB 偏离。
- 分类（暂定，未校准）：<0.2 CB独有；0.2–0.7 部分同步；≥0.7 同步；Kraken 窗口内成交 <5 笔记为"参照稀疏"；锚价超过 30 秒记为"无参照"。
- `lag_ms` = Kraken 极值时间 − CB 极值时间（正值 = Kraken 更晚），仅在幅度比 ≥0.2 时参考；两所时钟误差未知，只看百毫秒级。
- 对照组：同一天、同样影线条件、但成交量 <10 BTC 的秒。
- Kraken 只有成交、没有历史盘口；"Kraken 没动"指成交价没动，不等于报价没动。

### 2026-10-31 至 2026-11-19 全区间结果

Kraken 共 3,020,312 笔，ID 连续。383 个 CB 事件中 378 个可比（5 个从窗口锚价到极值不足 0 bps，跳过）：同步 147、部分同步 166、CB独有 61、参照稀疏 4。1 秒收益相关在滞后 0 秒最高（0.51），Kraken 滞后 1 秒为 0.28、领先 1 秒为 0.05。

- 秒位（每分钟第几秒）分布与均匀分布无显著差异（χ²=50.3，59 自由度，5% 临界≈77.9）；11-18 18:39:26–18:41:26 的 60 秒节奏是个例。
- CB独有（60 秒内去重 57 个）：窗口内 Kraken 只走了 CB 幅度的 8%（中位），但 60 秒后已跟到 55%。CB 收盘后 60 秒沿影线方向延续，平均 −7.9 bps（自助法 95% 区间 −14.1 至 −2.0），反转率 42%；下影线 34 个、上影线 23 个两边都是延续。
- 部分同步、同步两类收盘后 60 秒均值都接近 0。
- 局限：仅 19 天、处于 77k→62k 单边下跌行情；测了 3 类 × 2 个时长，存在多重比较；收益是收盘价标记，不是可成交损益。

## 归档与还原（`archive.py`）

原始逐笔数据库不常驻磁盘，只保留无损归档（2026-11-19 归档后，data 从 3.4 GB 降到 127 MB）：

| 归档 | 笔数 | 成交 ID | 大小 |
|---|---:|---|---:|
| `data/archive/coinbase_btcusd_2026-10-31_2026-11-19.csv.gz` | 22,342,165 | 1113023025–1135365189，连续 | 114.2 MB |
| `data/archive/kraken_xbtusd_2026-10-31_2026-11-19.csv.gz` | 3,020,449 | 113698541–116718989，连续 | 17.9 MB |

- 格式：第一行 `#` + JSON 元数据（表结构、小数位、笔数、ID 范围、`runs` 采集记录全文）；之后每行一笔，按 ID 排序，ID、时间、价格为与上一笔的差值，价格和数量为定点整数。
- 归档时 `verify` 已逐行比对原库全部字段（原始字符串）和 `runs` 表，全部一致；用还原出的 Kraken 库重跑 11-18 对比，输出与原结果逐字节相同。
- `output/2026-10-31_to_2026-11-19/bars_1s.csv` 已压缩为 `bars_1s.csv.gz`（62 MB，SHA-256 与原文件一致）；`kraken.py compare --bars` 可直接读 `.gz`。
- 原库和中间库（早期未完成的回补、compact/fast/blind/parallel_probe 测试库、截图窗口的 `trades.sqlite`）均已删除；它们的内容都包含在完整库里。

需要重新分析时先还原（约几分钟）：

```powershell
python -X utf8 archive.py unpack --archive data/archive/coinbase_btcusd_2026-10-31_2026-11-19.csv.gz --db data/coinbase.sqlite
python -X utf8 archive.py unpack --archive data/archive/kraken_xbtusd_2026-10-31_2026-11-19.csv.gz --db data/kraken_xbtusd.sqlite
```

`research.py analyze` 需要未压缩的 `--db`；还原的 CB 库带 `runs` 表，覆盖检查照常工作。新数据回补完成后，用 `archive.py pack` + `verify` 归档，再删除原库。
